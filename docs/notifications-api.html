System Overview & Architecture

How the notification system is structured and why

The Washermann notification system is a unified, five-channel messaging layer built inside a NestJS global module. Every business event that matters to a customer, rep, vendor, or admin triggers the appropriate channel mix automatically — the calling code only calls one method.

🏗️ Architecture

NotificationsModule is decorated @Global(), meaning its NotificationsService is injectable everywhere without re-importing. Calling code simply injects the service and calls a semantic method like notifyOrderPlaced().

🔥 Fire & Forget

Every notification call is wrapped in a fire-and-forget pattern. A transient Resend outage or an expired FCM token will never crash a business transaction. Failures are logged as warnings only.

📋 DB-Backed Templates

50+ default templates seed the notification_templates table on first startup. Admins can update content, styling, subject lines, and HTML via the REST API without redeployment.

🎨 Handlebars Rendering

Template bodies use {{variableName}} syntax. The TemplateService compiles and renders them at send time with real data. DB templates take precedence over code defaults.

📧 Email — Resend

Provider: Resend — modern transactional email API. Free tier: 100 emails/day, 3,000/month. Paid from $20/month.

Format: Full responsive HTML generated via the buildEmailHtml() helper. Admins can override the HTML body entirely via the template API. The email renders a header, styled content block, and footer.

When it fires: Order confirmations, delivery notifications, payout confirmations/failures, vendor verification, pricing approvals — all events where a permanent record or rich formatting is valuable.

Not used for: Real-time alerts (push/WhatsApp are faster). Short operational messages (use SMS).

💬 SMS — Termii

Provider: Termii — Nigerian-focused SMS gateway with excellent local delivery rates. Sender ID registration required for production.

Format: Plain text, concise (under 160 characters where possible to avoid multi-part billing). No links unless absolutely necessary.

When it fires: Order placed (backup to push for users without the app), order delivered, payout approved, assignment broadcast to rep/vendor, vendor verification. SMS fires when the user has a phone number registered.

Billing note: SMS has per-message cost. Use for high-value events only — the system does not send SMS for every status change.

🔔 Push — Firebase Cloud Messaging (FCM)

Provider: Firebase Admin SDK — supports iOS (APNs bridged), Android, and Web.

Requirements: The mobile app must call PATCH /users/me/fcm-token at login and whenever the device token refreshes. Stale tokens (uninstalled app) are handled gracefully — logged as WARN, not errors.

When it fires: Every actionable event — order placed, rep/vendor assigned, pickup, delivery, earnings, payouts, assignments. Push is the primary real-time channel for app users.

Priority: Android: high (wakes device). iOS APNs: badge: 1, sound: default. Channel ID: washermann_default.

Multi-cast: PushService.sendMulti(tokens[], title, body) supports up to 500 tokens per batch via sendEachForMulticast.

📱 In-App Notifications

Storage: PostgreSQL table in_app_notifications. Each notification is a row with userId, title, body, type, isRead, readAt, and optional metadata JSONB.

Types: order | assignment | payout | account | general

When it fires: Every event fires an in-app notification (it's free and persistent). The mobile app polls GET /notifications/me/unread-count on launch to show the badge count.

Retention: Notifications are never auto-deleted — they form a permanent audit trail visible to the user.

🟢 WhatsApp — Twilio

Provider: Twilio WhatsApp Business API. For sandbox testing, use the Twilio sandbox number. For production, you need a WABA (WhatsApp Business Account) approved number.

Format: Rich text with *bold* and _italic_ markdown. Emoji supported. Can include multi-line messages.

When it fires: High-engagement events — order placed, rep assigned, pickup, delivery, assignment broadcasts, payout approved. WhatsApp has ~98% open rates in Nigeria.

Phone format: Numbers must be in E.164 format (e.g. +2348012345678). The system auto-prefixes whatsapp: for Twilio.

All endpoints under /admin/notification-templates require Admin role. Templates are keyed by (key, channel) pairs — e.g. order.placed.customer + email.

FCM Token Registration

Register and refresh device tokens for push notifications

PATCH /users/me/fcm-token User
Registers or updates the authenticated user's FCM device token. Call this at login and whenever onTokenRefresh fires in the mobile app.

Request Body

{ "token": "fcm_device_token_from_firebase_sdk" }

Response

{ "message": "FCM token updated" }
⚠️
Pass "token": "" (empty string) or "token": null to clear the token (e.g. on logout). This prevents push delivery to a signed-out device.

Direct API Testing

cURL examples for every notification-related endpoint

Replace {{BASE_URL}} with your server address (e.g. http://localhost:3000) and {{TOKEN}} with a valid JWT from a login response.

Step 0 — Get a Token

# Login as customer
curl -s -X POST {{BASE_URL}}/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"customer@test.com","password":"Test1234!"}' \
  | jq '.access_token'

# Save to shell variable
export TOKEN="eyJhbGciOiJ..."
export BASE_URL="http://localhost:3000"

Step 1 — Register FCM Token (Mobile App Required)

curl -X PATCH ${BASE_URL}/users/me/fcm-token \
  -H "Authorization: Bearer ${TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"token":"dJHGk1...FCMTokenFromFirebase"}'

Step 2 — Trigger a Notification (Place an Order)

Placing an order fires: email + SMS + push + in-app + WhatsApp to the customer simultaneously.

curl -X POST ${BASE_URL}/orders \
  -H "Authorization: Bearer ${TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{
    "areaId":          "area-uuid-here",
    "serviceType":     "wash_and_fold",
    "bagSize":         "medium",
    "pickupAddress":   "15 Admiralty Way, Lekki Phase 1",
    "scheduledPickupAt": "2024-05-10T09:00:00Z"
  }'

# Expected: 201 Created
# Side effects: 5 notification channels fire in background (fire-and-forget)

Step 3 — Check the In-App Inbox

# Get all notifications (page 1)
curl -s ${BASE_URL}/notifications/me \
  -H "Authorization: Bearer ${TOKEN}" | jq '.data[0]'

# Get unread count (for badge)
curl -s ${BASE_URL}/notifications/me/unread-count \
  -H "Authorization: Bearer ${TOKEN}"
# → {"count": 1}

Step 4 — Mark Notifications Read

# Mark single notification read

curl -X POST ${BASE_URL}/notifications/me/${NOTIF_ID}/read \
  -H "Authorization: Bearer ${TOKEN}"

# Mark ALL read
curl -X POST ${BASE_URL}/notifications/me/read-all \
  -H "Authorization: Bearer ${TOKEN}"
# → {"updated": 1}

Step 5 — Admin: List Notification Templates

# Get admin token first
export ADMIN_TOKEN="eyJhbGci..."

# List all templates
curl -s ${BASE_URL}/admin/notification-templates \

  -H "Authorization: Bearer ${ADMIN_TOKEN}"

curl -X PATCH ${BASE_URL}/admin/notification-templates/${TEMPLATE_ID} \

# Find the SMS template for order.placed.customer
curl -s "${BASE_URL}/admin/notification-templates?key=order.placed.customer&channel=sms" \

Scenario B: Rep Assignment Broadcast

Shows what happens when the system broadcasts a job to reps.

🛵 Reps: Batch broadcast → first accepts wins
  1. System scores available reps in the area → picks top 3.
  2. All 3 reps receive: SMS + Push + In-App + WhatsApp simultaneously. "New job available! Order WM-001 — 15 Admiralty Way. Tap to accept!"

  5. Customer receives Push + In-App + WhatsApp: "Emeka has been assigned to your order."
  6. If nobody accepts → system re-broadcasts to next batch. If all batches exhausted → admin email alert.

Design Decisions & Justification

Why the system is built this way

1. Why five channels instead of one or two?

Different channels serve different functions and user contexts:

ChannelStrengthLimitation
EmailRich formatting, permanent record, works offlineNot seen immediately; low urgency
SMSWorks on feature phones; high open rate even without dataPer-message cost; 160-char limit
PushInstant; app badge; works when app is closedRequires app install + token
In-AppAlways available; searchable history; no costOnly seen when app is open/refreshed
WhatsApp98%+ open rate in Nigeria; conversational contextRequires Twilio WABA approval

A customer without the app still gets SMS + WhatsApp. A customer with the app gets Push + In-App for instant feedback. Email provides a paper trail for financial events. This redundancy ensures no critical notification is missed regardless of device or connectivity state.

2. Why fire-and-forget?

Notification delivery is non-critical to the transaction outcome. A failed email must never roll back an order or payout. The fire(fn, logger, label) wrapper ensures:

  • The business operation returns immediately (low latency for the user)
  • Notification errors are logged for observability but suppressed from the HTTP response
  • Temporary provider outages (Resend/Termii/FCM/Twilio) don't cause user-facing 500 errors

In a future production hardening, failed notifications would be written to a retry queue (Redis/BullMQ) for at-least-once delivery. The current implementation is appropriate for initial launch.

3. Why DB-backed templates with code fallbacks?

Hardcoding templates in source files means every copy change requires a code review, build, and deployment — an unnecessary engineering bottleneck for marketing/operations teams. The DB-backed system allows:

  • Non-engineers to update copy, subject lines, and colours via the admin API (or future UI)
  • A/B testing of different message variants
  • Seasonal branding changes without touching code
  • Per-template enable/disable without deployment

The hardcoded DEFAULT_TEMPLATES array serves as the safety net — if a DB record is corrupted or missing, the system falls back to working defaults and continues operating.

4. Why Handlebars for variable substitution?

Handlebars was chosen over simple string interpolation because:

  • Familiar syntax — {{variableName}} is readable by non-developers who edit templates in the admin UI
  • Safe compilation — malformed templates don't crash the process; the service falls back to the raw string
  • Extensible — Handlebars supports helpers for date formatting, conditionals, loops if needed in future
  • No eval — unlike template literal tags, Handlebars does not expose arbitrary code execution

5. Why is the module @Global()?

NotificationsService needs to be called from OrdersService, AssignmentService, PayoutsService, and VendorsService — which are in completely separate modules. Without @Global(), every module would need to explicitly import NotificationsModule, adding boilerplate and potential for circular import issues. Making it global is the NestJS-idiomatic pattern for cross-cutting concerns like logging, notifications, and analytics.

6. Why seed templates on startup?

The TemplateService.seedDefaults() method runs on OnModuleInit. It only inserts rows that don't already exist (idempotent). This means:

  • A fresh environment gets all 50+ templates automatically — zero manual setup
  • New templates added in a code update are automatically provisioned on next deploy
  • Existing admin customisations are never overwritten (the check is findOne() → skip if exists)
  • Safe to run on every server restart

7. Channel selection logic per event

Not all channels fire for every event — the selection is deliberate:

  • High-value financial events (payout approved, order placed) → all 5 channels. These are the most important touchpoints and warrant maximum reach.
  • Real-time status updates (rep assigned, picked up) → push + in-app + WhatsApp. These are transient state changes; email would be noise.
  • Internal admin alerts (no reps, new payout request) → email only. Admin checks email; push/WhatsApp to a generic admin address isn't meaningful without a dedicated device.
  • Rep earnings → push + in-app only. Reps use the app; SMS costs money and isn't needed for every earning event.

Complete .env configuration for all notification channels

# ─── Email (Resend) ─────────────────────────────────────────────
RESEND_API_KEY=re_your_api_key_here
RESEND_FROM_EMAIL=no-reply@washermann.com
RESEND_FROM_NAME=Washermann

# ─── SMS (Termii) ───────────────────────────────────────────────
TERMII_API_KEY=TLyour_api_key_here
TERMII_SENDER_ID=Washermann          # Must be approved in Termii dashboard

# ─── Firebase FCM (Push Notifications) ──────────────────────────
FIREBASE_PROJECT_ID=washermann-prod
FIREBASE_CLIENT_EMAIL=firebase-adminsdk-xxxx@washermann-prod.iam.gserviceaccount.com
FIREBASE_PRIVATE_KEY=-----BEGIN RSA PRIVATE KEY-----\nMIIEo...\n-----END RSA PRIVATE KEY-----
# ↑ Use literal \n for newlines in .env; the config restores real newlines

# ─── WhatsApp (Twilio) ───────────────────────────────────────────
TWILIO_ACCOUNT_SID=ACyour_account_sid_here
TWILIO_AUTH_TOKEN=your_auth_token_here
TWILIO_WHATSAPP_FROM=whatsapp:+14155238886   # Sandbox or approved number

# ─── Admin notifications ─────────────────────────────────────────
ADMIN_NOTIFICATION_EMAIL=ops@washermann.com  # Receives payout/escalation alerts

# ─── Deep link (used in invite emails) ──────────────────────────
DEEP_LINK_BASE=washermann://app

Obtaining Credentials

ServiceWhere to GetNotes
Resend resend.com/api-keys Verify your sending domain in the Resend dashboard for best deliverability.
Termii termii.com → Dashboard → API Register your Sender ID. DND (Do Not Disturb) lists are automatically respected.
Firebase Firebase Console → Project Settings → Service Accounts → Generate Key Download the JSON file; extract project_id, client_email, private_key.
Twilio WhatsApp console.twilio.com → Messaging → WhatsApp Use sandbox for testing. Production requires WABA approval from Meta (1-2 weeks).
✅
Testing checklist:
  1. Verify all env vars are set in your .env file
  2. Start the server and check logs for "initialised" messages from each provider
  3. Register FCM token via PATCH /users/me/fcm-token
  4. Place a test order and check all 5 channels within 10 seconds
  5. Verify in-app inbox via GET /notifications/me
  6. Test admin template update → preview → verify email changed
